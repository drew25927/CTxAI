# 🧪 팀 셀프테스트 — `/interim`·`/film` 임계값 1차 보정

**작성:** 개발(세션) · 2026-09-14 · **갱신:** 개발(세션) · 2026-09-26 (0단계 "웹캠 표정 인식 자체 확인" 게이트 추가 + 팀원 3명 각자 혼자 진행 가능하도록 구조 변경)

**목적:** 20명 규모 정식 헤드셋 파일럿(11/7 발표 1주 전 목표) 전에, **팀원 2~3명만으로 지금 당장** 판정 임계값의 1차 값을 잡는다. 정식 파일럿은 이 1차 값이 맞는지 검증하는 용도로 미뤄도 된다 — 지금 임계값 보정 자체를 막고 있는 건 아니다.

**전제**: `/interim`·`/film` 둘 다 HUD에 등급/최종 배합 뒤에 숨은 **원시 숫자**가 이미 보이도록 만들어 뒀다. `/judge-v2`(개발자용 판정 대시보드)에는 이번에 **표정 인식 실시간값**(공포/웃음 점수가 매 프레임 그대로 뜸)도 추가했다. 이 문서는 그 숫자를 "무슨 값이 나와야 정상인지" 기준으로 읽는 법과, 읽은 값으로 실제 상수를 고치는 법을 정리한 것이다.

**이 문서는 순서가 중요하다 — 0단계를 통과하기 전에는 1단계 이후로 넘어가지 말 것.** S2·S4(놀람/정서) 판정은 전부 웹캠이 표정을 제대로 읽는다는 전제 위에 서 있다. 그 전제 자체가 맞는지 아무도 확인 안 한 채로 타임라인 전체를 연기하며 최종 등급만 보는 건, 원인(표정 인식이 안 됨)과 결과(엉뚱한 등급)를 구분 못 하게 만든다. **0단계는 개발 세션(AI)이 대신 확인할 수 없다** — 이 샌드박스 브라우저엔 실제 카메라가 없어서 `getUserMedia()`가 항상 `Permission denied`로 막힌다(직접 시도해서 확인됨). 실제 웹캠이 있는 사람이 해야 한다.

## 0. 필수 게이트 — 웹캠이 표정을 실제로 읽는지 먼저 확인 (팀원 각자, 5분씩)

이 단계는 시나리오 연기가 전혀 필요 없다. **화면을 보면서 표정만 지으면 된다** — S1·S3·S5(머리방향) 테스트처럼 화면 밖을 봐야 하는 문제가 없어서 완전히 혼자, 실시간으로 확인 가능하다.

**⭐ 로컬 서버 필요 없음 — 팀 대시보드에서 바로 한다.** 이 확인 전용 페이지를 새로 만들어 배포해 뒀다: **https://busstop-team.vercel.app/facecheck** (`/todo` 대시보드의 "판정 확인용" 그룹에도 카드로 링크돼 있음). **한 사람만 해보고 결과를 공유하는 게 아니라, 팀원 각자 자기 노트북·자기 카메라로 직접 열어서 확인해야 한다** — 카메라·조명·자리마다 인식이 다르게 될 수 있어서다.

1. 팀원 각자 자기 브라우저에서 위 주소 접속.
2. "카메라 켜고 확인 시작" 클릭 → 카메라 권한 허용.
3. 90초 관찰 창이 도는 동안, 화면에 뜨는 실시간 숫자를 본다:
   ```
   공포 0.XXX · 웃음 0.XXX
   ```
4. 아래 두 표정을 각각 지어보고, 숫자가 기대한 쪽만 올라가는지 확인한다.

| 지어볼 표정 | 기대 결과 |
|---|---|
| 무표정(기본값) | 공포·웃음 둘 다 낮게(0에 가깝게) |
| **무서운 표정** — 눈을 크게 뜨고 눈썹을 위로 올린다(놀란 표정) | **공포**만 뚜렷이 올라감, 웃음은 그대로 |
| **웃는 표정** — 활짝 웃으며 볼을 조인다(진짜 웃음) | **웃음**만 뚜렷이 올라감, 공포는 그대로 |

**판정 기준(`lib/behaviorSense.js`의 `FEAR_SHAPES`/`AMUSEMENT_SHAPES`)**: 공포는 `eyeWideLeft/Right`+`browInnerUp`(눈 크게+눈썹 위), 웃음은 `mouthSmileLeft/Right`+`cheekSquintLeft/Right`(입꼬리+볼 조임) 블렌드셰이프 조합이다. 위 표의 표정이 정확히 이 조합을 겨냥한 것.

### 통과/실패 기준

- **통과**: 두 표정에서 각각 의도한 숫자만 확실히 올라간다 → 1단계(`/interim`)로 넘어가도 된다.
- **실패** — 아래 중 하나라도 해당하면 **여기서 멈추고, 코드 쪽(개발 세션)에 먼저 알릴 것**. 이 상태로 뒤의 시나리오 테스트를 해봐야 등급이 왜 그렇게 나왔는지 원인을 못 가른다:
  - 숫자가 표정과 상관없이 거의 안 움직인다(카메라 각도·조명 문제일 수도 있음 — 먼저 정면·밝은 곳에서 재시도).
  - 무서운 표정에서 웃음도 같이 오르거나, 웃는 표정에서 공포도 같이 오른다(블렌드셰이프 조합이 서로 겹친다는 뜻 — `기존 (v1.1 시절부터)` 배운 것 중 `jawOpen` 같은 사례와 동일 유형의 문제).
  - "얼굴 없음"이 계속 뜬다(카메라 각도/거리 문제 — 정면에서 다시 시도 후에도 안 되면 보고).

## 1. 준비물 + 배역 배정

- 노트북 + 웹캠·마이크 각자 1대 (헤드셋 있으면 더 좋음 — 없어도 드래그로 대부분 테스트 가능)
- 로컬 서버 — **각자 자기 컴퓨터에서** 이 저장소를 pull 받아 띄운다(같은 서버를 셋이 같이 쓰는 게 아니다):
  ```bash
  cd ctxai-busstop-xr-audio-proto
  npm run dev        # /interim, /judge-v2 등 일반 페이지
  npm run film       # /film 전용 (셸 환경변수 문제 우회)
  ```
- **각자 0단계부터 통과한 뒤** 아래로 진행.

### 1.1 배역 배정 — 팀원당 1개씩, 혼자 진행

| 팀원 | 배역 | 목표 |
|---|---|---|
| 팀원 1 | **공포형** | `/interim`·`/film` 5개 사건 전부 H(공포)로 채점되게 반응 |
| 팀원 2 | **호기심형** | 전부 C(블랙코미디)로 채점되게 반응 |
| 팀원 3 | **차분형** | 전부 R(로맨스)로 채점되게 반응 |

배역은 고정하지 않아도 된다 — 시간 되면 서로 배역을 바꿔서 한 번씩 더 해보면(교차 검증) 더 좋다. 다만 **한 번에 한 사람은 자기 배역 하나만** 하면 된다(셋이 동시에 각자 다른 배역으로 돌리면 30분 안에 6개 화면 다 채워짐).

### 1.2 혼자 진행하는 법 — 화면 녹화부터 켠다

0단계(표정)와 달리, 2절 이후의 S1·S3·S5(머리방향) 사건은 화면 밖(왼쪽/오른쪽 뒤)을 봐야 해서 혼자면 연기하면서 동시에 HUD를 읽을 수 없다. 그래서 **연기 시작 전에 macOS 화면 녹화부터 켜고**(`Cmd+Shift+5` → 화면 전체 기록, 또는 브라우저 개발자 도구 켜둔 채로), 대본대로 반응한 뒤 **녹화본을 다시 보면서** 표를 채운다. HUD의 "S_ 원시값" 줄이나 `/film`의 사건 목록 줄은 짧게 스쳐가므로 녹화 없이 실시간으로 받아 적으려 하지 말 것.

파트너가 있으면(2명이 같이 있는 경우) 굳이 나눌 필요 없이 한 명이 연기하는 동안 다른 한 명이 화면을 보고 받아 적어도 되고, 그냥 각자 녹화로 진행해도 된다 — 둘 다 허용.

### 1.3 결과 취합

각자 채운 표(2·3절)를 이 문서에 자기 이름으로 표시해 추가하거나, 팀 채널에 스크린샷/표로 공유한다. 셋 다 끝나면 한 사람이 세 결과를 합쳐 "의도한 등급이 나왔나?" 칸을 최종 정리하고, 안 맞은 신호만 골라 2.4·3.3의 상수를 고친다.

## 2. `/interim` (2분 20초) 테스트

### 2.1 타임라인 — 이 시각에 이 사건이 온다

| 시각 | 사건 | 신호 | 방위 |
|---|---|---|---|
| 0:15 | 판초 인물이 카페 쪽에서 걸어온다 (판정까지 계속) | **S1** 관심 | -35° (왼쪽) |
| 0:35 | 트럭이 물웅덩이를 튀긴다 | **S2** 놀람 | 정면(웹캠·마이크) |
| 0:55 | 바람에 포스터가 파닥인다 | **S3** 호기심 | +72° (오른쪽 뒤) |
| 1:13 | 고양이가 나타난다 | **S4** 정서 | 정면(웹캠·마이크) |
| 1:35 | 개구리가 운다(안 보임, 소리만) | **S5** 경계 | +135° (오른쪽 훨씬 뒤) |
| 1:55 | 판정 확정 | | |

### 2.2 배역별 연기 대본 — 1.1에서 배정받은 자기 배역만 읽으면 됨

**① 공포형** — 목표: 전부 H로 채점되는 것
- S1: 판초 인물 쪽을 거의 안 본다. 가끔(몇 초마다) 불안하게 힐끗거리기만.
- S2: 트럭이 튈 때 움찔하며 몸을 뒤로 젖힌다. 놀라서 "헉" 소리를 낸다.
- S3: 포스터 쪽은 잠깐 보고 만다(오래 안 봄).
- S4: 고양이가 무섭다는 표정을 짓는다(찡그림, 몸 사림) — 0단계에서 확인한 "무서운 표정"과 같은 것.
- S5: 개구리 소리에 크게 놀라 **헤드셋이면 벌떡 일어선다.** (데스크톱 드래그로는 기립 신호 자체가 안 잡힌다 — 헤드셋으로만 확인 가능)

**② 호기심형** — 목표: 전부 C로 채점되는 것
- S1: 판초 인물을 힐끗 보고 만다(오래 안 봄, 대신 여러 번 재확인).
- S2: 트럭 튀는 거 보고 "어?"하고 짧게 웃거나 탄성.
- S3: 포스터 쪽으로 몸을 돌려 3초 넘게 유심히 읽는다.
- S4: 고양이 보고 웃는다(재밌어함) — 0단계에서 확인한 "웃는 표정"과 같은 것.
- S5: 개구리 소리에 천천히 돌아보되 놀라지 않는다.

**③ 차분형** — 목표: 전부 R로 채점되는 것
- S1: 판초 인물을 3초 이상 담담하게 계속 본다.
- S2: 트럭 튀는 거 거의 반응 없음.
- S3: 포스터 쪽은 안 본다(관심 없음).
- S4: 고양이를 편하게 오래 지켜본다(웃지도 무서워하지도 않고).
- S5: 개구리 소리에 별 반응 없음.

### 2.3 기록표 — 각자 자기 배역 칸만 채우고, 나중에 합친다

HUD에 뜨는 원시값을 그대로 적는다(1.2 참고 — 녹화본 보면서 채울 것). 셋이 각자 자기 배역 열(공포형/호기심형/차분형 중 하나)만 채우면 되고, 1.3에서 한 사람이 합친다.

| 신호 | 지금 코드 기준값 | 공포형 실측 | 호기심형 실측 | 차분형 실측 | 의도한 등급이 나왔나? |
|---|---|---|---|---|---|
| S1 (look, retreat, recheck) | `lookSec≥3→A`, `recheck→B` | | | | |
| S2 (fear, amuse, startle, mic) | `startle>0.12→A`, `startle>0.05→B` | | | | |
| S3 (look, retreat, recheck) | `lookSec≥3→A` | | | | |
| S4 (fear, amuse, sustain, mic) | `amuse>0.5→D`, `fear>0.5→C` | | | | |
| S5 (retreat, 기립 여부) | 기립→A, `retreat>0→B` | | | | |

**⚠️ 알려진 설계 이슈 — 미리 알고 보면 덜 헷갈림**: 시뮬레이션(`npm run test`의 `sim-interim.mjs`)으로 미리 확인해보니, **S2에서 "단발로 크게 나는 소리"는 무섭게 지른 비명이든 놀라서 낸 탄성이든 마이크만으로는 구분이 안 되고, 지금 코드는 이걸 전부 "C(웃음·탄성)"로 채점**한다(`lib/interimGrader.js`의 `gradeS2FromWebcam` 맨 위 분기). 진짜 비명과 즐거운 탄성을 구분하려면 소리 크기(RMS) 말고 다른 신호(표정 등)가 같이 필요하다 — 이 셀프테스트에서 공포형이 트럭 사건에서 예상과 다르게 나오면 이게 원인일 수 있다. 급하면 마이크 분석 로직을 손보고, 아니면 "웹캠 표정이 더 강하면 표정을 우선한다" 같은 규칙을 기획과 상의해서 추가할 것.

### 2.4 값을 고치는 곳

- `lib/interimGrader.js` — 등급 경계값 (예: `if (startle > 0.12) return "A"`의 `0.12`)
- `lib/interimMic.js` — 소리 크기·반복 판단 기준
- `lib/standUpSense.js` — 기립 인정 기준(`RISE_M`, `RISE_WINDOW_SEC`)
- `lib/behaviorSense.js` — 0단계에서 표정 인식 자체가 잘못됐다고 나오면 여기의 `FEAR_SHAPES`/`AMUSEMENT_SHAPES` 블렌드셰이프 조합부터 의심할 것

고친 뒤에는 `npm test`를 다시 돌려서(특히 `test-interim.mjs`) 로직 자체가 안 깨졌는지 확인.

## 3. `/film` (5분) 테스트

타임라인·매핑표는 이미 `반응형_실시간_영화.md` §3·§5에 자세히 있다. 여기선 **HUD에서 뭘 읽으면 되는지**만 정리한다.

### 3.1 화면에서 읽는 법

사건이 끝나면 HUD 하단 "사건 목록"에 한 줄씩 쌓인다:
```
포스터   안 봄 · 속도0°/s · 후퇴0.00m
물보라   봤음 1.1s · 속도140°/s · 후퇴0.07m · 회복1.5s
```
- **속도**: `STARTLE_YAW_VEL`(기본 140°/s)과 비교 — 진짜 놀라서 홱 돌아볼 때 몇 °/s가 찍히는지 본다.
- **후퇴**: `RETREAT_M`(기본 0.07m)과 비교 — 헤드셋 위치가 뒤로 몇 m 밀리는지.
- **회복**: `SLOW_RECOVERY_SEC`(3.0초)·`FAST_RECOVERY_SEC`(1.5초)과 비교.
- 줄 위에 마우스를 올리면(또는 길게 누르면) 지금 코드에 들어간 임계값 4개가 툴팁으로 뜬다.

### 3.2 배역별 연기

## 4. 참고 — 합성 시뮬레이션과의 관계

`npm test`를 돌리면 `sim-headpose.mjs`(`/film`)·`sim-interim.mjs`(`/interim`)가 자동으로 "겁많은/호기심많은/차분한" 가상 관객 셋을 합성 데이터로 흉내 내서, 지금 로직이 의도한 대로 갈리는지 사람 없이 확인해준다. **이건 로직 점검용이지 숫자 실측이 아니다** — S2·S4의 웹캠 표정값도 시뮬레이션에서는 손으로 지어낸 그럴듯한 숫자일 뿐, 진짜 카메라가 진짜 표정을 읽은 값이 아니다(그래서 0단계가 따로 필요하다). 이 문서(팀 셀프테스트)가 실측을 대신한다. 셋 다 하는 게 이상적이다: 시뮬레이션으로 로직 버그를 먼저 잡고, 0단계로 표정 인식 자체를 확인하고, 1~3단계 셀프테스트로 숫자를 1차로 잡고, 정식 파일럿으로 검증한다.
